# Pull request conventions

## Title
Same format as commits: `<TICKET-ID> <type>[scope]: <description>` — a PR
is normally scoped to one ticket (or a tight group of related tickets),
so the title should read like the "headline" commit of the set.
If a PR spans multiple tickets, list all ticket IDs: `A1/A3 feat(profile): ...`

## Description template
```md
## Summary
1-3 sentences: what this PR does and why, in plain terms. Assume the
reader hasn't read the ticket.

## Ticket(s)
- A1 — Profile data model (link to ticket doc/section if applicable)

## Changes
- Bullet list of what changed, grouped logically (not a raw commit list —
  summarize, the commit history already has the detail)

## How this was tested
- What you actually ran: `pytest`, manual check via `/docs` (Swagger UI),
  specific scenarios verified (e.g. "confirmed cross-school query returns
  403, not empty list")
- If a test category from the testing skill doesn't apply to this PR
  (e.g. no auth/tenant surface touched), say so explicitly rather than
  leaving it silently unaddressed

## Out of scope / follow-up
- Anything you noticed but deliberately didn't fix here, so it isn't lost
  and isn't assumed to be "done"

## Checklist
- [ ] Follows commit conventions (small, ticket-prefixed commits)
- [ ] Tests pass locally (`pytest`)
- [ ] Migration reviewed by hand, not just autogenerated and run blind (if applicable)
- [ ] Multi-tenant scoping confirmed (if this PR touches student/teacher/school data)
- [ ] STATUS.md updated
```

## Size
A PR should map to one ticket, or a small tightly-related group — not a
batch of unrelated tickets bundled to save review overhead. If a PR is
getting large enough that "Changes" needs more than ~6-8 bullets, that's
a signal it should have been split, same principle as commits.

## Before opening
Re-read the diff once as a reviewer would, not just as the author —
catch stray debug code, commented-out blocks, or an accidental unrelated
file change before asking for review rather than after.
